## lif-kernel Bugs / Limitations

### FEATURE REQUEST: JSON import attributes
`import data from './file.json'` without `with {type: 'json'}` is common in
bundler-built code (Webpack, Metro, etc.) but browsers require the import
attribute. lif-kernel's Babel transpiler should detect imports where the
specifier ends in `.json` and add `with {type: 'json'}` automatically.
Latest Chrome fully supports import attributes (`with {type: 'json'}`).
This is the standards-forward solution — no wrapping JSON as JS needed.
Affected: @react-native-vector-icons (all icon sets import glyphmap .json files)
  e.g. `import glyphMap from "../../glyphmaps/Entypo.json"`
Workaround: none currently (blocks App.tsx from loading)

### FEATURE REQUEST: Asset imports (Webpack-compatible)
`import icon from './icon.png'` is not valid ESM but is a widely supported
bundler convention. Webpack, Vite, Metro, Parcel, esbuild all detect imports
by file extension and return a JS module exporting the asset's URL.
lif-kernel should do the same for Webpack compatibility — detect known asset
extensions and return: `export default "<served URL of the file>"`.
Webpack has no built-in default list — each project configures its own rules.
Common convention (from Create React App, Metro, etc.):
  images:  .png .jpg .jpeg .gif .webp .avif .ico .bmp .svg
  fonts:   .woff .woff2 .eot .ttf .otf
lif-kernel should pick a reasonable set of extensions to handle.
The served URL should point to the actual binary file on the lif-kernel
server so the browser can fetch it when used (e.g. as <img src>).
Affected: @react-navigation/elements (5 PNG imports), possibly others.
Workaround: manually patch the importing file to use `const x = ''` instead.

### BUG: Service worker state corruption after lmod error
When any module resolution triggers `TypeError: Cannot read properties of
undefined (reading 'lmod')`, the service worker's internal state becomes
permanently corrupted. ALL subsequent requests (even for previously working
modules like react, react-native) return 500 with the same lmod error.
Only fix: restart Chrome with a fresh --user-data-dir to get a new SW.
This makes debugging very painful — one bad import poisons everything.
Expected: errors should be isolated per-request, not corrupt global state.
Repro: load the app, trigger a module that causes lmod error, then try
  fetching any other ?mjs or ?imp URL.

### LIMITATION: file: dep subpath imports ignore physical files
When package.json has `"pkg": "file:./stubs/pkg"` and the code imports
`pkg/sub/path`, lif-kernel resolves it via ?imp to:
  `export * from "/.lif/local/.../stubs/pkg/index.js?mjs"`
It always re-exports from the main entry, ignoring any physical file at
stubs/pkg/sub/path.js. The dep's package.json `exports` field is also
not honored.
Affected: @arkade-os/sdk/repositories/realm, @arkade-os/sdk/adapters/expo,
  @arkade-os/boltz-swap/repositories/realm.
Workaround: put ALL exports (including subpath-specific ones) in the root
index.js of the stub. The physical subpath files are never used by ?imp.

### LIMITATION: file: dep with bc-bech32 causes 500 on ?imp
Even after converting bc-bech32 to ESM, the entry
  `"bc-bech32": "file:./blue_modules/bc-bech32"`
causes 500 "Cannot read properties of undefined (reading 'match')" when
anything tries to resolve it via the ?imp endpoint.
Workaround: don't import bc-bech32 by npm name. bc-ur/dist files now use
relative paths (../../bc-bech32/dist/index.js) instead. The package.json
entry could potentially be removed entirely.

## JS Coding Conventions (same as lif-wallet)
- No spaces around arrow functions: (a, b)=>code
- No spaces around === and ==
- Use == for string and simple number comparison
- No .then() — use await (async IIFE inside useEffect for cleanup)
- No statements on same line as if ()
- No space after async: async()=>...
- catch(e){ — no space before (
- Section comments: // Section Name (no box-drawing)
- if/for/while: statement on next line, not same line
